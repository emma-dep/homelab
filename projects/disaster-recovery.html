CASE STUDY 01

Backup &
Disaster Recovery

A service-aware backup system for critical homelab infrastructure, built with Bash, systemd and SQLite and backed by automatic failure notifications.

Linux Bash systemd SQLite rsync ntfy

THE PROBLEM

Backups needed to survive more than a file deletion.

Several important services run on Pandora, including Vaultwarden, Pi-hole, Jellyfin and Home Assistant. Losing the server's internal drive could therefore mean losing service configuration, application databases and automation state.

Simply copying directories was not enough. Several applications use active SQLite databases, backups should not silently write to the wrong filesystem if the backup disk is unavailable, and failures needed to be visible rather than discovered during an actual recovery.

DESIGN

Service-aware snapshots.

A dedicated external SSD is mounted as the backup target. Individual backup scripts handle each service independently, allowing each application to be backed up according to its own requirements.

Services Vaultwarden · Pi-hole · Jellyfin · Home Assistant
→
Backup Scripts Bash · rsync · SQLite
→
Backup SSD Timestamped snapshots

IMPLEMENTATION

Designed around failure conditions.

01

Mount-point protection

Backup scripts verify that the dedicated backup filesystem is mounted before writing data, preventing backups from accidentally filling the server's root filesystem when the external disk is unavailable.

02

Consistent SQLite backups

Active databases are copied using SQLite's backup mechanism instead of blindly copying live database files.

03

Integrity verification

Database snapshots are checked with SQLite integrity checks before the backup job is considered successful.

04

Automatic scheduling

systemd timers execute backups automatically with persistent scheduling so missed runs can execute after the system becomes available again.

05

Retention management

Timestamped snapshots are automatically rotated using a defined retention period rather than accumulating indefinitely.

06

Failure notifications

Failed systemd backup units trigger an independent notification path through ntfy running on another server, delivering an alert to my phone.

systemd timer sanitized example 
[Timer]
OnCalendar=daily
Persistent=true
RandomizedDelaySec=15m

[Install]
WantedBy=timers.target

Persistent=true allows a missed scheduled run to execute after the server becomes available again.

RandomizedDelaySec prevents every scheduled backup job from starting at exactly the same moment.

Bash mount safety check 
BACKUP_ROOT="/mnt/backups"

if ! mountpoint -q "$BACKUP_ROOT"; then
    echo "Backup filesystem is not mounted." >&2
    exit 1
fi

Before writing anything, the script verifies that the external backup filesystem is actually mounted.

Without this guard, a missing external disk could cause data to be written into the empty mount directory on the server's root filesystem instead.

SQLite database validation 
sqlite3 "$SOURCE_DB" ".backup '$BACKUP_DB'"

RESULT=$(sqlite3 "$BACKUP_DB" "PRAGMA integrity_check;")

if [ "$RESULT" != "ok" ]; then
    echo "Database integrity check failed." >&2
    exit 1
fi

SQLite's backup mechanism creates a consistent snapshot of an active database. The resulting copy is then checked before the backup job is considered successful.

VALIDATION

Testing the unhappy path.

The notification chain was tested using a deliberately failing disposable systemd service. This verified that a unit failure triggered the OnFailure dependency, executed the notification service and successfully delivered the alert.

Backup jobs were also run manually during setup and their resulting snapshots and database integrity checks were verified before relying on scheduled execution.

LIMITATIONS & NEXT STEPS

A backup isn't finished until recovery is understood.

The current system protects against common local failures but does not yet constitute a complete 3-2-1 backup strategy. The backup SSD remains physically located with the server and is currently unencrypted.

Planned improvements include documented restore procedures, periodic restore testing, encryption at rest and eventually an additional off-site copy.

WHAT I LEARNED

Reliability means designing for what goes wrong.

This project moved my backup strategy beyond simply copying files. It required thinking about database consistency, filesystem state, permissions, scheduling, retention, monitoring and how failures become visible.

It also reinforced an important operational lesson: a successful backup job is only one part of disaster recovery. Restore procedures and recovery testing are equally important.
