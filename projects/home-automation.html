CASE STUDY 04

Home Automation &
Local Voice

A self-hosted Home Assistant environment with local speech recognition, text-to-speech and custom functionality running on my own Linux infrastructure.

Home Assistant Docker Whisper Piper Python Linux

THE GOAL

Build an assistant I can actually extend.

I wanted Home Assistant to become more than a dashboard for devices. The goal was to create a locally hosted assistant whose speech pipeline and custom functionality I could understand, modify and integrate with the rest of my homelab.

Keeping the core voice-processing components local also gave me an opportunity to experiment with speech infrastructure without making cloud services a requirement for the basic pipeline.

ARCHITECTURE

Speech enters, an intent comes out.

Voice Input Spoken command
→
Whisper Speech to text
→
Home Assistant Intent & automation
Home Assistant Response
→
Piper Text to speech
→
Client Spoken response

Home Assistant, Whisper and Piper run as separate containerized services on Pandora. The components communicate over the local infrastructure while keeping persistent Home Assistant configuration outside the container lifecycle.

IMPLEMENTATION

Separate components with clear responsibilities.

01

Home Assistant

Home Assistant provides the central automation and intent layer while maintaining persistent configuration on the host.

02

Local speech recognition

Whisper provides speech-to-text processing as a dedicated service rather than embedding recognition directly into the Home Assistant container.

03

Local text-to-speech

Piper provides locally hosted speech synthesis for generated responses.

04

Containerized deployment

The application stack is managed through Docker, separating individual services while keeping deployment reproducible and easier to troubleshoot.

05

Persistent configuration

Home Assistant configuration is stored outside the application container and is included in the homelab's automated backup system.

06

Custom integration development

I began extending Home Assistant with a custom reminder integration, including configuration-flow and intent handling components rather than relying exclusively on existing integrations.

CUSTOM DEVELOPMENT

Moving from configuration to code.

One of the goals of the project is voice-created reminders. I began implementing this as a custom Home Assistant component, separating integration setup, constants and intent handling into individual Python modules.

This turned the project into more than a deployment exercise: Home Assistant became a platform I could extend with my own functionality.

OPERATIONS

The assistant is part of the infrastructure.

The Home Assistant configuration is covered by the same backup strategy as other important services. Its SQLite database is backed up consistently and checked for integrity rather than being copied blindly while active.

Treating the application as part of the wider homelab also means thinking about persistence, recovery and service dependencies rather than only whether the UI currently loads.

CURRENT DEVELOPMENT

The project is deliberately unfinished.

The current stack provides the foundation for local voice processing and custom Home Assistant development. The next stage is completing and validating the reminder workflow and improving the client experience around voice interaction.

I document unfinished work explicitly because distinguishing deployed functionality from planned functionality is important when operating real systems.

WHAT I LEARNED

Self-hosting becomes much more interesting when you build on it.

This project connected container administration with application configuration, local AI services and Python development.

It also reinforced the value of separating components by responsibility: speech recognition, automation logic and speech synthesis can be operated and troubleshot independently.
