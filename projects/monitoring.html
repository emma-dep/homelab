CASE STUDY 03

Monitoring &
Alerting

Independent infrastructure monitoring using a dedicated Debian server, Uptime Kuma and authenticated ntfy push notifications.

Debian Docker Uptime Kuma ntfy DNS Linux

THE PROBLEM

A failed service is useless if nobody notices.

As the homelab grew, checking individual services manually stopped being practical. Core infrastructure could fail while appearing normal until I happened to use the affected service.

I wanted centralized monitoring that could detect failures across multiple machines and notify me without depending on the same host being monitored.

ARCHITECTURE

Monitoring lives outside the systems it watches.

Pandora Core services
→
Demeter Uptime Kuma
→
ntfy Push notifications

Demeter is a separate headless Debian system dedicated to monitoring and notifications. This means a failure of a service on Pandora does not automatically remove the system responsible for detecting that failure.

IMPLEMENTATION

Monitoring several layers of the lab.

01

Host availability

Ping monitors check whether important machines are reachable on the network, providing a basic distinction between host failure and individual application failure.

02

Application monitoring

HTTP monitors check services including Jellyfin, Vaultwarden, Sonarr, Prowlarr and qBittorrent rather than assuming a reachable host means its applications are healthy.

03

DNS monitoring

DNS resolution is tested independently against the local resolver, allowing failures in internal name resolution to be detected separately from web services.

04

Authenticated notifications

ntfy uses authenticated access rather than an anonymously writable notification topic.

05

Mobile delivery

Alerts are delivered to my phone so infrastructure failures become visible without repeatedly checking the monitoring dashboard.

06

Persistent containers

Monitoring services run through Docker with persistent application data and automatically recover across normal host reboots.

INTEGRATION

One notification service, multiple failure sources.

ntfy is not limited to Uptime Kuma. Pandora's backup system independently sends authenticated failure notifications to the ntfy instance running on Demeter.

This gives the lab a reusable notification layer: monitoring software can report service outages while systemd can report failed infrastructure jobs through the same destination.

SECURITY

Monitoring shouldn't become another exposed service.

Incoming firewall access to Demeter's management and monitoring services is restricted to the local network. ntfy requires authentication, and credentials are stored outside the public portfolio repository.

Internal addresses, credentials and other operational details are intentionally omitted from this public documentation.

WHAT I LEARNED

“The server is up” doesn't mean the service is healthy.

Building the monitoring system made the distinction between host availability, application availability and supporting infrastructure much clearer.

It also demonstrated why monitoring should be designed with failure domains in mind. Separating monitoring from the main application server makes it much more useful when that server is the thing that breaks.
