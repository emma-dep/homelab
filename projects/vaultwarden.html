CASE STUDY 02

Private Password
Infrastructure

A self-hosted Vaultwarden deployment using containers, private DNS and internally trusted HTTPS while keeping the service restricted to my own infrastructure.

Vaultwarden Docker Caddy Pi-hole DNS TLS

THE PROBLEM

Self-hosting passwords without sacrificing HTTPS.

I wanted to migrate my password vault from a hosted Bitwarden account to infrastructure under my own control while preserving encrypted HTTPS access for clients on my local network.

The challenge was not simply running Vaultwarden in a container. The deployment also required reliable name resolution, certificate trust and a reverse proxy while avoiding unnecessary public exposure of the service.

ARCHITECTURE

Private DNS meets private PKI.

IMPLEMENTATION

Building the trust chain.

01

Containerized application

Vaultwarden runs as a Docker container with persistent application data separated from the container lifecycle.

02

Private DNS

Pi-hole provides local DNS resolution so clients can reach the service through a stable private hostname rather than relying on a raw IP address.

03

Reverse proxy

Caddy terminates HTTPS and proxies requests to the Vaultwarden container, keeping TLS configuration separate from the application itself.

04

Internal certificate authority

Caddy's internal PKI provides certificates for the private service. The root certificate is trusted on authorized client devices so browsers and applications can validate the connection normally.

05

Restricted registration

Public account registration is disabled after the required vault account was configured.

06

Independent backups

Vaultwarden's persistent data is incorporated into the homelab backup system, including a consistent SQLite database snapshot and integrity verification.

TROUBLESHOOTING

HTTPS working isn't the same as HTTPS being trusted.

During deployment I encountered certificate trust problems across different clients. This required separating several concepts that initially looked like one problem: certificate generation, server-side TLS configuration, hostname resolution and client-side trust.

I verified DNS resolution independently, checked the reverse proxy configuration and installed the internal CA certificate on authorized clients. I also encountered a client import issue caused by mismatched certificate and key material, which helped reinforce the distinction between a server's private key, leaf certificate and CA trust certificate.

SECURITY DECISIONS

Expose only what needs to be exposed.

The password manager is intended as a private service rather than a public website. Internal DNS and locally trusted certificates provide a usable HTTPS endpoint without requiring the application itself to be directly published to the internet.

Credentials, private keys, authentication secrets and internal addressing are deliberately excluded from this portfolio and its public repository.

WHAT I LEARNED

TLS is a chain, not a checkbox.

This project gave me practical experience with the relationship between DNS, TLS certificates, certificate authorities, reverse proxies and application containers.

More importantly, troubleshooting the deployment taught me to isolate each layer independently rather than treating “the website isn't secure” as a single problem.
